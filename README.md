# infobez
infobez 1 sem maga

Консольное приложение на C++17 с трёхфакторной аутентификацией
(пароль → TOTP → код на email). После входа пользователь может шифровать свои
сообщения «Кузнечиком» или RSA-32768, просматривать и расшифровывать их,
а также выгружать PDF-отчёт со всеми сообщениями и их расшифровкой.

## Сборка

macOS (Apple Silicon или Intel):

```bash
brew install gmp        # длинная арифметика для RSA-32768
make                    # собирает ./auth3fa
make selftest           # проверка всех алгоритмов на эталонных векторах
./auth3fa
```

Ubuntu/Debian: `sudo apt install libgmp-dev libcurl4-openssl-dev && make`.

Вручную, без Makefile (macOS + Homebrew):

```bash
g++ -std=c++17 -O2 -I$(brew --prefix gmp)/include -o auth3fa auth3fa.cpp \
    -L$(brew --prefix gmp)/lib -lcurl -lgmp -pthread
```

## Файлы

| Файл | Что внутри |

| `auth3fa.cpp` | основная программа: 3FA, панель администратора, меню сообщений, хранилище ключей |
| `kuznyechik.hpp` | «Кузнечик» (ГОСТ Р 34.12-2015) + режимы CTR и OMAC (ГОСТ Р 34.13-2015), реализация с нуля |
| `rsa_gmp.hpp` | RSA-32768 на GMP: параллельная генерация ключа, OAEP, расшифрование через CRT |
| `pdf_writer.hpp` | генератор PDF без внешних библиотек, встраивает TrueType-шрифт (кириллица) |
| `secure_random.hpp` | криптографический ГСЧ ОС (`/dev/urandom`, `BCryptGenRandom`) |
| `gost3410.hpp` | ЭЦП ГОСТ Р 34.10-2012 на эллиптической кривой (GMP) |
| `asn1.hpp` | кодирование и разбор ASN.1 DER для сертификата и CMS |
| `pdf_signature.hpp` | сертификат X.509, контейнер CMS, проверка подписи PDF |
| `auth.cpp` | первый этап (только логин/пароль, SHA-256), оставлен без изменений |

## Меню после входа

```
1. Зашифровать новое сообщение      -> выбор: Кузнечик или RSA-32768
2. Список моих сообщений
3. Расшифровать сообщение
4. Сформировать PDF-отчёт           -> report_<логин>_<дата>.pdf
5. Сведения о ключах
6. Статистика и производительность  -> таблицы по сообщениям + замеры
7. Проверка по контрольным примерам ГОСТ
8. Проверить подпись PDF-файла
9. Выйти из аккаунта
```

Каждый пользователь видит только свои сообщения.

## Проверка по ГОСТ и замеры производительности

```bash
./auth3fa --selftest   # 50 контрольных примеров ГОСТ + 13 дополнительных проверок
./auth3fa --bench      # скорость Стрибога, Кузнечика и RSA-32768 (с генерацией ключа)
```

**Контрольные примеры** (50 шт., значения из текстов стандартов):

| Стандарт | Что сверяется |
|---|---|
| ГОСТ Р 34.11-2012, прил. А | Стрибог-512 и Стрибог-256 на примерах M1 и M2 |
| Р 50.1.113-2016 | HMAC-Стрибог-256 и HMAC-Стрибог-512 |
| ГОСТ Р 34.12-2015, прил. А.1 | Кузнечик: S, R, L (по 4 шага), константы C1–C4, раундовые ключи K1–K10, блок туда и обратно |
| ГОСТ Р 34.13-2015, прил. А.1 | ECB (4 блока туда и обратно), CTR, имитовставка MAC |
| ГОСТ Р 34.10-2012, прил. А, пример 1 | ЭЦП: открытый ключ Q = d·P, подпись r и s, проверка подписи |

`--selftest` и пункт 7 меню выводят по каждой проверке подробный отчёт:
- какие параметры ГОСТ использованы (π, τ, матрица A, константы C, коэффициенты l,
  поле GF(2^8), константа B_128 и т.д.) и в каком файле и на какой строке программы
  они заданы (номера строк подставляются при компиляции, поэтому всегда актуальны);
- входные данные из приложения к стандарту;
- значение, полученное программой, и ожидаемое по ГОСТ;
- итог: совпало или нет.

В конце идёт сводная таблица.

Эти 50 проверок выполняются **при каждом запуске программы**, как
самотестирование в сертифицированных криптомодулях. При любом расхождении
программа печатает таблицу с эталоном и полученным значением и не запускается.

Время шифрования сохраняется вместе с каждым сообщением. У сообщений,
зашифрованных до этого обновления, оно не известно (в таблицах «-»).

**Замеры** (`--bench` или пункт 6 меню) выводятся ASCII-таблицами. По каждой
операции показываются: число повторов, среднее, медиана, мин/макс, разброс
(σ/среднее) и скорость в МБ/с или операциях в секунду. Перед замерами идёт
прогрев.

- **Стрибог:** 512 и 256 бит на 64 Б / 1 КБ / 1 МБ, HMAC, PBKDF2.
- **Кузнечик:** развёртка ключа, блок туда и обратно, CTR и OMAC на 1 МБ,
  шифрование сообщения целиком.
- **RSA-32768:** шифрование, расшифрование через CRT в несколько потоков и в
  одном потоке, прямое c^d mod n без CRT (видно, во сколько раз CRT быстрее),
  OAEP целиком.
- **Генерация ключа RSA:** статистика поиска простых для каждого числа. Число
  окон решета, сколько кандидатов прошло решето (~93% отсеивается), тестов
  Ферма, проверок BPSW+MR, время. Сохраняется вместе с ключом и попадает в PDF.

## Криптография

**Кузнечик** — ключ 256 бит, режим гаммирования CTR со случайным 64-битным IV,
имитовставка OMAC 128 бит на отдельном ключе (Encrypt-then-MAC). Преобразования
S и L объединены в 16 предвычисленных таблиц, поэтому раунд — это 16 обращений
к таблице и XOR. Скорость около 50 МБ/с на одно ядро. Реализация побайтно совпадает
с контрольными примерами ГОСТ Р 34.12/34.13 (см. `--selftest`).

**RSA-32768** — модуль 32768 бит, e = 65537, дополнение RSAES-OAEP (RFC 8017)
с хешем Стрибог-512. Длинные сообщения режутся на блоки по 3966 байт.
Чтобы это вообще работало за разумное время:

- **многопростой RSA** (RFC 8017 §3): модуль 32768 бит собран из 4 простых
  по 8192 бита. Это константа `RSA_PRIMES` в `auth3fa.cpp`; `2` даёт классический
  n = p·q. Возведение в степень на 8192 битах в ~4–7 раз дешевле, чем на 16384,
  поэтому ключ генерируется в ~4 раза быстрее, а расшифровывается в ~4–5 раз
  быстрее. Стойкость задаёт длина n: для множителей по 8192 бита метод
  эллиптических кривых бесполезен (его рекорд ~270 бит);
- арифметика — GMP (Карацуба/Тоом-Кук, ассемблерные ядра под ARM64/x86-64);
- генерация простых: решето по ~1,08 млн малых простых (до 2²⁴) отсеивает ~93%
  составных кандидатов до дорогих тестов. В том же решете сразу исключаются
  кандидаты p ≡ 1 (mod e);
- выжившие кандидаты проверяются параллельно на всех ядрах: сначала тест Ферма
  по основанию 2, затем BPSW + Миллер–Рабин (`mpz_probab_prime_p`);
- расшифрование по китайской теореме об остатках (обобщённая формула Гарнера):
  возведения в степень по каждому простому идут параллельно, по потоку на простое;
- закрытая экспонента возводится через `mpz_powm_sec` (постоянное время,
  защита от атак по времени). Результат CRT перепроверяется возведением
  в степень e (защита от атаки сбоев Белкора).

Ключ RSA генерируется один раз на пользователя, при первом выборе RSA.
Замеры на слабой машине (2 ядра, облачный x86):

| Операция | 2 простых (классика) | 4 простых (по умолчанию) |
|---|---|---|
| генерация ключа | 146 с | 35 с |
| шифрование блока 4096 байт | 3,5 мс | 3,3 мс |
| расшифрование | 2,05 с | 0,46 с |

На Mac с 8–10 ядрами генерация займёт заметно меньше, обычно секунды–десятки
секунд. Время случайно: оно зависит от того, как далеко от случайной стартовой
точки окажется простое число.

**Хранение ключей** (`vault/<hex(логин)>/`). Из пароля пользователя функцией
PBKDF2-HMAC-Стрибог-512 (20 000 итераций, соль 128 бит) выводится ключ KEK.
На нём «Кузнечиком» (CTR+OMAC) зашифрованы ключ сообщений и закрытый ключ RSA.
Без пароля прочитать сообщения нельзя, даже имея все файлы.
Поэтому при **восстановлении пароля** (когда старый пароль неизвестен) хранилище
расшифровать невозможно. Программа предупреждает об этом и удаляет его.

Попутно табличным методом ускорено линейное преобразование L в Стрибоге
(в ~18 раз). Также добавлен вариант Стрибог-256: он отличается от 512 только
начальным вектором и усечением результата.

## PDF-отчёт

В начале отчёта идут ASCII-таблицы, набранные моноширинным шрифтом:

- сводка по сообщениям (размеры, время шифрования и расшифровки, целостность);
- статистика по алгоритмам (объёмы, коэффициент расширения шифртекста);
- итоги проверки по контрольным примерам ГОСТ;
- статистика генерации ключа RSA.

Других графических элементов (линий, маркеров, эмодзи) в отчёте нет. Эмодзи
из текста сообщений при выводе в PDF удаляются, а в отчёте отмечается, сколько
их было.

Для каждого сообщения в отчёте есть номер, дата, алгоритм, параметры (IV,
имитовставка), шифртекст в hex, расшифрованный текст и результат проверки
целостности. В конце приложен открытый ключ RSA и его отпечаток. Кириллица
работает за счёт встраивания системного шрифта: на macOS это Arial и
Courier New. Другой `.ttf` можно указать в переменных окружения `PDF_FONT` /
`PDF_FONT_MONO` или положить `font.ttf` рядом с программой.

## Электронная подпись PDF (ГОСТ Р 34.10-2012)

Каждый PDF-отчёт подписывается электронной подписью пользователя. Подпись
встроена в сам файл, так же как в документах, подписанных в Adobe Acrobat или
КриптоПро.

- **Алгоритм:** ГОСТ Р 34.10-2012, 256 бит, кривая
  `id-tc26-gost-3410-2012-256-paramSetB` (CryptoPro-A). Хеш — Стрибог-256.
  Реализация с нуля (`gost3410.hpp`), сверена с контрольным примером из
  приложения А к стандарту.
- **Ключ подписи:** создаётся при первом входе в хранилище пользователя. Закрытый
  ключ хранится зашифрованным на ключе из пароля, как и остальные ключи.
  К ключу выпускается самоподписанный сертификат X.509 (CN = логин,
  срок действия 5 лет).
- **Формат:** поле подписи PDF (`/ByteRange` + `/Contents`) с контейнером CMS
  (PKCS#7 detached). Внутри контейнера:
  - сертификат;
  - хеш документа и время подписи;
  - сама подпись.

  OID алгоритмов — по Р 1323565.1.024-2019 / RFC 9215 (`asn1.hpp`,
  `pdf_signature.hpp`).
- **Что подписано:** весь файл, кроме самого значения подписи. Поэтому изменение
  любого байта или дописывание данных в конец делают подпись недействительной.

Проверка:

```bash
./auth3fa --verify report_user_20261026_120000.pdf   # без входа в систему
```

То же доступно в пункте 8 меню; там дополнительно показывается, подписан ли
файл ключом текущего пользователя. Программа проверяет четыре вещи:
- подпись охватывает весь файл;
- хеш документа совпадает с хешем в подписи;
- подпись ГОСТ Р 34.10-2012 верна;
- самоподпись сертификата верна.

Сразу после формирования отчёта программа автоматически проверяет его подпись.

Сторонние программы видят подпись, например `pdfsig` из poppler:
```
Signature Field Name: Подпись ГОСТ Р 34.10-2012
Signer full Distinguished Name: CN=student,OU=auth3fa,O=infobez
Total document signed
```
Математически проверить ГОСТ-подпись могут только программы с поддержкой
российской криптографии (КриптоПро и т.п.). Обычный Adobe Reader без
КриптоПро покажет «не удалось проверить»: он не знает ГОСТ-алгоритмов. Кроме
того, сертификат самоподписанный и не выпущен аккредитованным удостоверяющим
центром, поэтому юридической силы квалифицированной ЭП у подписи нет.

## Важно про безопасность репозитория

`config.txt` содержит пароль приложения Gmail в открытом виде, а `users.txt` —
хеши паролей и TOTP-секреты. Их не нужно хранить в git: они добавлены в
`.gitignore`. Если они уже попали в репозиторий, отзовите пароль приложения в
настройках Google-аккаунта и удалите файлы из истории.
